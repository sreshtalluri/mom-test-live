## Problem Statement

The `mom-test` skills repo (v0.3.0) already has a paste-driven live mode
(`mom-test-next-question live`): during a call, the founder pastes a few lines and gets
back a Signal/Why/Say-next/Don't-say nudge. It works, but it requires manually
switching windows and typing mid-call, which is itself a distraction from listening —
the thing the whole book is about. The user wants something that watches the call
directly and only interrupts when it actually catches something, the way Cluely-style
tools work, plus an after-call debrief so the founder can act on next steps immediately
rather than wait.

## What Makes This Cool

Not "Cluely for customer interviews." A **conversation contamination firewall**: every
existing meeting-copilot in the landscape search answers "what should I say to THEM"
(interview answers, sales lines). This tool's job is the opposite — catch the
**founder's own** speech violating the Mom Test rules (pitching, leading, accepting
compliments as evidence, explaining instead of listening) before it contaminates the
conversation, and only then. Quiet by default: no dashboard to read mid-call. It shows
something only when a rule trips, then gets out of the way again.

## Constraints

- Native downloadable app, not a hosted service — user explicitly wants "proper
  software others can download," not a SaaS the maintainer runs and gets billed for.
- Free tool, bring-your-own-API-key for whatever eventually needs a key. Zero recurring
  cost to the maintainer at any scale. A future paid/hosted tier is an open door, not a
  requirement — architecture must not preclude it, but must not require it either.
- Real consent design required, not simplified away — recording/transcribing a call
  the founder is on may require the other party's consent depending on jurisdiction.
  This needs an explicit, mandatory, **unskippable** step **before any processing of
  the file begins** — not after transcription, not a default-on toggle.
- Reuse over rebuild, but reuse means something specific and different depending on
  what's being reused (see "What reuse actually means" below) — two rounds of
  adversarial review on this doc both found real problems exactly where "reuse" was
  vague, so this section is now load-bearing, not decoration.
- "Invisible" means invisible-until-triggered coaching for the founder, not deception
  about whether the call is being recorded. Positioning must not lean on
  "undetectable/stealth" as the value prop — the value prop is the coaching cue.
- This is a separate desktop-app project (new GitHub repo), not a `SKILL.md` file. It
  calls into or vendors logic from the `mom-test` skills repo as its brain, rather than
  living inside it.

## What reuse actually means (resolved after two rounds of adversarial review)

`mom-test-debrief` and `mom-test-memory` are agent-facing prompt files. They're written
for a coding agent that has real, ongoing access to the founder's project files — reads
`discovery/assumptions.md` to reuse real IDs, offers to run `mom-test-memory record`
interactively, asks `[Y/n]` and waits for an answer. A one-shot API call from a desktop
CLI has none of that: no file access, no ability to ask a question and wait, and a
literal copy of either skill's prompt text produces either wrong output (guessing at
`discovery/`'s contents) or dangling, unanswerable prompts in the response.

Round 1 of this design tried "vendor the prompt as a system-prompt passthrough" for
`mom-test-debrief` specifically. Round 2's review checked that against the actual file
and found it doesn't hold: the debrief prompt's own §0 and §8 assume exactly the file
access and interactivity a one-shot call doesn't have, and a debrief generated blind to
the founder's real `discovery/assumptions.md` risks silently mis-tagging evidence onto
the wrong real assumption ID once handed off.

**Resolved: v0 does not call an LLM at all, and does not generate a debrief.** Its only
job is producing a clean, readable transcript file from a recording or an existing
transcript. Both `mom-test-debrief` and `mom-test-memory` are 100% reused by simply
telling the founder to run them, unmodified, inside their own coding agent — which
already has the real file access, the real current version of both skills, and the
ability to answer their own `[Y/n]` prompts. This isn't a compromise; it's the correct
shape once you accept that "reuse" for an agent-facing skill means "hand the input to
the real thing," not "extract and replay its prompt from a context that can't act on it."

## Premises

Agreed by the user (D4), all five, no simplification:

1. The coach's job is self-monitoring the founder's own speech, not generating answers
   about the customer.
2. Quiet by default: no dashboard to read mid-call; surfaces only when a rule trips,
   then disappears.
3. Call recording/transcription needs a real consent design (some jurisdictions require
   the other party's consent too).
4. Reuse over rebuild: fork/vendor an existing OSS stealth-overlay base (OpenCluely)
   rather than building capture + STT + overlay from scratch for v1; for v0, reuse
   `mom-test-debrief` and `mom-test-memory` by handing off to the founder's own agent,
   not by re-implementing or replaying their prompts (see above).
5. Separate project, separate repo, calling into the skills repo as its brain.

Plus the cost-model decision from this session (D6): free tool, bring-your-own-key,
hybrid architecture for v1 (audio and transcription/diarization run fully local; only
short already-transcribed text snippets go to a cloud classifier). A future paid/hosted
tier is an explicit, deferred option — the provider layer must be pluggable so a hosted
tier can be added later as one more provider, not a rewrite. **v0 turns out to need no
API key at all** — see below.

## Cross-Model Perspective

Codex (`model_reasoning_effort=high`), condensed:

- **Coolest version not yet considered:** named it a "conversation contamination
  firewall" — nudges are corrections ("You're pitching. Ask about the last time
  instead"), not answers. The after-call version should be a "forensic evidence pack":
  transcript, founder-contamination moments, customer facts, evidence-rung tags,
  recommended next interviews — not a meeting summary.
- **What reveals the user's excitement:** "just a small nudge and guidance when we
  catch something" — not transcription, not summaries, not a dashboard. The excitement
  is real-time judgment: the app noticing a subtle interview failure at the exact
  moment it matters.
- **50% OSS building blocks:** fork **OpenCluely** (MIT, Electron) for the stealth
  overlay + audio/screen capture plumbing — it already implements the OS-level
  screen-capture-exclusion APIs (`NSWindowSharingNone` on macOS, `WDA_EXCLUDEFROMCAPTURE`
  on Windows; no Linux equivalent). For diarization: **Deepgram** (cloud, fastest,
  production-grade today) or **Diart** (real-time, local, built for streaming) +
  whisper.cpp for local transcription. Missing 50% either way: speaker role assignment,
  latency control, confidence thresholds/cooldowns, and the actual two-track
  classification.
- **Weekend build:** fork OpenCluely, Deepgram streaming STT+diarization, vendor Mom
  Test rules as the classifier, local JSONL session log, markdown export. Explicitly
  skip for v1: full local/offline transcription, Linux capture invisibility, CRM
  integrations, calendar-bot joining, auto-writing into `discovery/` without review, a
  fancy dashboard, multi-user sync, perfect diarization, legal automation beyond clear
  consent UX.

Claude's synthesis and what changed after discussion with the user and two rounds of
adversarial review: agreed with the diarization/overlay architecture for v1, reframed
the cost model into a hybrid after pulling real pricing, reframed "stealth" as a
positioning risk to avoid, and — after review found this doc's reuse claims kept
breaking on contact with the real skill files — landed on the simplest version that
actually survives scrutiny: v0 does no LLM work of its own and no diarization of its
own; it hands the founder a clean transcript and two exact commands to run in their own
agent.

## Real cost research (this session)

**v0 importer: $0, no API key needed at all.** Its only external dependency is local
whisper.cpp (bundled, offline, free). There is no cloud call in v0's pipeline — the
debrief and the `discovery/` write both happen later, inside the founder's own coding
agent session, using whatever model that agent is already running on (not billed by
this tool at all).

**v1 live coach**, per 30-minute call:

| Path | Transcription + diarization | Classifier | Total |
|---|---|---|---|
| Cloud (Deepgram + Groq) | ~$0.20–0.30 (Deepgram streaming STT ~$0.0068–0.0097/min incl. diarization) | ~$0.005 (Groq Llama 3.1 8B, ~180 checks × ~550 tokens) | **~$0.20–0.30** |
| Local (whisper.cpp + Diart + local classifier) | $0 (whisper.cpp: 7–33x real-time on Apple Silicon with Core ML; Diart: purpose-built streaming, real but tunable latency) | $0 | **$0** |
| **Hybrid (chosen for v1)** | $0 (local whisper.cpp + Diart; audio never leaves the device) | ~$0.005 (Groq, text snippets only) | **~$0.005** |

At 1,000 calls/month, cloud-only v1 would run $200–300/month to whoever hosts it; the
hybrid v1 runs about $5/month, paid by each founder on their own (often free-tier
eligible) Groq key, not the maintainer, and v0 costs nothing at all to anyone. The
bigger real cost is still **shipping a signed macOS app for v1**: Apple's $99/year
developer fee for code-signing and notarization, deferred until there's real usage
(v0's CLI binary doesn't trigger the same Gatekeeper friction a `.app` does).

## Approaches Considered

### Approach A: Live overlay first, macOS-only, unsigned
Fork OpenCluely, macOS only, local whisper.cpp+Diart, BYOK Groq classifier, unsigned
`.app` via GitHub Releases. Effort M. Delivers the actual ask first; ships the riskiest,
least-validated engineering (diarization latency/quality, and a founder-violation
classifier that doesn't exist yet) before anyone's used it.

### Approach B: Cross-platform, signed, day one
macOS + Windows both day one, pay for signing/notarization immediately, pluggable
provider abstraction built in from the start. Effort L. Most "proper software" from day
one; weeks and real money spent before a single real user has tried anything.

### Approach C: After-call importer first, live overlay second (chosen)
Ship a v0 that turns a recording or transcript into a clean file the founder feeds to
their own coding agent — no LLM call, no diarization, no `discovery/` write inside the
tool itself. Only then build the live overlay (Approach A's shape, with a real
founder-violation classifier informed by v0's usage). Effort S for v0, then A's scope
for v1.

## Recommended Approach

**C.** Same eventual destination as A, sequenced so the two expensive, unvalidated
parts (the live overlay's real-time plumbing, and a founder-violation classifier that
doesn't exist yet) get built with evidence instead of hope. This is itself a Mom Test
move: don't build the risky thing before validating the cheap thing, applied to the
tool's own roadmap.

### v0 — After-call transcript prep (CLI)

Pipeline order below is canonical — the same order everywhere in this document,
resolving round 2's finding that the table, Success Criteria, and Next Steps
previously disagreed with each other.

| Step | What it does |
|---|---|
| 1. Import | `mom-test-live import <file>` — accepts the file path only; **does not open, read, or process the file yet**. One file per run, v0 is explicitly single-file only; multi-file/batch is out of scope for v0 |
| 2. Consent gate | **Hard, unskippable, first real action, before the file is touched at all.** Terminal requires an explicit typed confirmation that the founder has the right to record/transcribe this call. No `--yes`/`--force` bypass in v0 |
| 3. Transcription | *Only reached after step 2.* If the input is audio: local whisper.cpp (bundled), offline. **On failure** (corrupt file, unsupported format, no speech detected): clear error, stop — never emit a transcript file from empty or garbage audio |
| 4. Speaker labels | **v0 does not diarize.** Two supported input shapes: (a) the founder provides a transcript that already has speaker turns (an export from Zoom/Otter/Meet, or typed with `F:`/`C:` prefixes — the same convention `mom-test-next-question live` already uses) — this is the fully-supported path, used as-is; (b) an audio file or a plain transcript with no speaker markers — whisper.cpp (or the plain file) produces a **flat, unlabeled** transcript, and the CLI prints an explicit warning that a real debrief needs speaker separation to score talk-ratio, pitching, and leading, plus the printed file path and one line of guidance: *"Open this file and add `F:`/`C:` prefixes to each line before handing it to mom-test-debrief, if you want accurate talk-ratio scoring."* No mid-run interactive editing loop, no new subcommand — the founder edits the file with their own editor on their own time, or skips it and accepts a less precise debrief. No fake diarization is attempted |
| 5. Output + hand-off | Writes the (possibly speaker-labeled) transcript to a file at a printed path, then prints the exact next step verbatim: *"Paste or attach the contents of &lt;path&gt; into your coding agent and say '/mom-test-debrief'. Once it finishes, say '/mom-test-memory record'."* Paste/attach, not a path argument, because neither `mom-test-debrief` nor `mom-test-memory` documents a file-path invocation syntax — they're written for pasted or attached notes. The CLI never calls an LLM and never touches `discovery/` — the founder's own agent does both, with real file access and the real, current skill files |
| Distribution | GitHub Releases, a single binary bundling whisper.cpp with a small/base model for zero-setup use out of the box; offers to download a larger model on request for founders who want better accuracy on noisy audio. No signing question for v0 (CLI binaries don't trigger the same Gatekeeper prompt a `.app` does) |

### v1 — Live overlay (once v0 has real usage)

Approach A's shape: fork OpenCluely, macOS-only initially, local whisper.cpp + Diart for
live transcription/diarization (v1 is where real diarization work happens — deliberately
not pulled forward into v0), BYOK Groq for a **new** founder-violation classifier
(informed by the Mom Test rules and by what v0's real transcripts reveal about common
mistakes, not a lift of `mom-test-next-question`'s customer-facing table, which
classifies the customer's statements, not the founder's). Nudge UI is quiet-by-default
and surfaces only `Signal / Why / Say next / Don't say` when a rule trips, with
confidence thresholds and a cooldown so it doesn't nag. Consent gate mandatory before
recording starts, every call, same hard-gate discipline and same ordering rule as v0
(consent before any capture begins). Session output feeds the same hand-off pattern as
v0 — a file plus exact commands for the founder's own agent, never a direct write.
Signing/notarization ($99/year) deferred until v0 shows real adoption; Windows support
deferred until there's demand, since local transcription there lacks Core ML
acceleration and would likely need a cloud-STT fallback via the user's own key.

## Open Questions

- **Windows local-transcription story.** whisper.cpp works everywhere but Core ML
  acceleration is Apple-only; Windows users may need a cloud-STT fallback (their own
  Deepgram key) to get comparable real-time performance. Deferred to v1/Windows-support
  decision.
- **Where does `mom-test-live` physically live relative to `mom-test`?** Separate repo
  (this design assumes that), but should it be a sibling under the same GitHub account,
  cross-linked from both READMEs? Yes — settle exact naming when the repo is created.
- **v0 language/runtime choice.** Not decided here — whatever makes bundling
  whisper.cpp and a single-binary GitHub Release easiest is fine; implementation
  detail, not a design decision needing sign-off.
- **Natural v0.5, not required for v0's definition of done:** a thin wrapper that
  automatically invokes the founder's coding agent CLI on their behalf (e.g.
  `claude -p "/mom-test-debrief ..."`), chaining transcript → debrief → record without
  the founder manually running two commands. Worth doing once v0 proves useful, but v0
  ships without it.

## Success Criteria

- v0: a founder can run `mom-test-live import <file>` on a real call recording or
  transcript, pass the consent gate *before anything else happens*, and get a clean,
  ideally speaker-labeled transcript file plus the exact two commands to run in their
  own coding agent — with zero API key required and zero cost to anyone.
- v0 handles, without emitting a broken or empty transcript: a corrupt/unsupported
  file, no speech detected, and a transcript with no speaker markers (explicit warning,
  not a fabricated diarization).
- v0 ships and gets used by at least a few real founders (not just the author) before
  any live-overlay engineering starts.
- v1: the overlay shows nothing during a quiet stretch of call, and shows exactly one of
  the four labelled lines within a few seconds of a rule violation, with a cooldown so
  it doesn't fire again immediately after.
- Consent gate appears before any file processing or recording begins, in both v0 and
  v1, hard-blocking, no flag to skip it, no default-on, same ordering rule both times.
